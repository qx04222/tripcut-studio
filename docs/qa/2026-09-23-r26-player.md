## 2. P-1(F-R25-01,P1)—— 完成

### 复现与根因
- 用 Homebrew mpv 0.41.0 CLI(与内置 libmpv 同版本)按应用的命令序列复现:`loadfile clipA` → `end=none` → `pause` → `seek 46.48 absolute+exact` → `end=51.9` → `pause=no` → 2.1 s 后 `pause=yes`,**4/4 卡 1871–1893 ms**;`end=53.1` 0/3(27–36 ms);同 51.9 但 1.0 s 后暂停 0/2。`--log-file` 关键行:
  - `ao/coreaudio: unable to set the input channel layout ... (-50)` → 回退 `ao/avfoundation`,`device buffer: 88200 samples` + `soft-buffer of 88200 samples`(44.1 kHz,约 4 s)。
  - 开播后 1.95 s 即 `audio draining` / `audio EOF reached`(此时画面在 ~48.4 s,离出点 51.9 约 3.5 s)——**音频解码比画面早一个 AO 缓冲撞到 `end` 围栏**,这就是 R25 没查清的「离出点 3.5 s 就 EOF」。此窗口里 `pause=yes` → `ao_set_paused(eof=true)` → `ao_drain` 等缓冲放完(~1.9 s)。出点 53.1 的 profile 上暂停点在窗口外,所以 0/9。
  - 对照:`--audio-channels=stereo` 后走 coreaudio(soft-buffer 8820 = 0.2 s),同序列 **0 ms ×4**;强制 `--ao=avfoundation --audio-channels=stereo` 仍 1.9 s ×3(证明是 AO 缓冲,不是声道本身);不发 Pause 直接 seek 无卡顿;`ao-reload` 后暂停 46 ms。
  - 所有夹具(clipA/B、clipC4k、synth4k50)音轨都是单声道 AAC。
- 应用内(新开关 `TRIPCUT_MPV_LOG_FILE`)修后日志:`AO: [coreaudio] 44100Hz stereo 2ch`、`device buffer: 1172`、`soft-buffer of 8820`。

### 修复
1. mpv 两档初始化选项加 `audio-channels=stereo`(optional):单声道上混后 coreaudio 接受,drain 上限 ~0.2 s。仅影响监视器预览,导出不经 mpv。
2. UI 与单条命令超时解耦:新命令 `sync`(渲染线程队列栅栏,不碰 mpv);前端 `sendPlayerCommandSettled`:命令响应超时(命令已在队列里、仍会执行)不再 `reportFailure` / 关播放器,改发 `sync` 等它真正处理完(最多 4 次 × 2 s),成功即继续同批命令;其它错误照旧;**绝不重发原命令**(step / `vf add` 不幂等)。`PlayerOverlay` 的命令循环与复播两处接入。
3. `TRIPCUT_MPV_LOG_FILE` 诊断开关(默认不开;注意每开一个新实例会覆盖同一文件)。
4. 拍板:切段路径**保留** Pause(同素材切段若不暂停,播放中 seek 落地后位置会走过入点半帧,状态机卡在 `frame` 阶段到 10 s 超时);根因修掉后 Pause 不再走长 drain,有 stereo + 栅栏两层兜底。

## 4. P-3(F-R25-05)—— 部分完成(HEVC 达标;长 GOP 源受解码下限约束)

### 耗时分解(基线,日志:Pause 命令 → `switch begin` → `switched`(新文件 PlaybackRestart))
- 去抖:实测 113–190 ms(100 ms + 50 ms 轮询粒度)。
- 载入原片:HEVC 夹具(关键帧间隔 0.24 s)52–140 ms,偶发 ~280 ms;h264 夹具 `clipC4k`(x264 默认 keyint 250 = **关键帧间隔 10 s**)101–1086 ms,**随距上一关键帧的距离线性增长**(精确 seek 要从关键帧解到目标帧,≈105 ms/秒 @4K25)。R25 的 830 ms 就是这个:出点 7.96 s 离关键帧 0 s 近 8 s。
- 修的过程中真机抓到第二个瓶颈:去抖压短后载入几乎每次 245–280 ms。mpv 日志 `mpv_render_context_render() not being called or stuck` —— 换源 FileLoaded 上渲染线程同步 `get_property`,与新文件 vo reconfig 互等到 vo_libmpv 的 200 ms 超时(基线里偶发的 ~280 ms 也是它)。实验包(去掉 stereo 只留新去抖)同样 9/11 慢,排除了 stereo。

### 修复
- 去抖 100 → 80 ms,渲染线程按剩余去抖精确唤醒。
- 换源 FileLoaded 不再同步读属性;宽高改观察事件、换源中屏蔽、在 PlaybackRestart 与来源同刻发布(角标不会出现「代理 2160p」半新半旧)。

### 真机数字(自动档素材模式,播 1.3 s → 暂停,Pause 命令 → 原片 PlaybackRestart;去掉打开素材那一次)
| 夹具 | 基线 | 修后 |
|---|---|---|
| 4K/50p HEVC Main10(GOP 0.24 s) | 20 次:p50 202–203 / p90 223–420 / max 428 ms | **10 次:p50 142 / p90 153 / max 170 ms**(载入 39–69 ms) |
| 4K/25p h264(GOP 10 s) | 15 次:p50 615–644 / p90 907–1068 / max 1218 ms | 10 次:p50 638 / p90 889 / max 1077 ms |
| 选段出点停住(4K h264 镜头 4.0–8.0,停 7.96) | R25:830 ms | 3 次:816 / 822 / 863 ms(载入 725–763 ms) |

- 结论:**关键帧间隔正常的素材(手机 / 相机常见 0.5–1 s)已稳在 ≤0.5 s**;长 GOP 素材的上限 = 去抖 80 ms + ~140 ms + ~105 ms × 距上一关键帧秒数(4K25 h264,M5),距关键帧 ≲3.5 s 才 ≤0.5 s。这是精确 seek 的解码下限,换源参数压不掉;可行方向(未做,需拍板):后台预开原片实例并跟随暂停点预解码(常驻第二个 4K 解码,内存/功耗代价大),或对长 GOP 素材的「暂停看原片」先显示最近关键帧再精确(时码短暂不准,违背 ±0.10 s)。
- 去抖不再往下压:拖进度条 / 逐帧之间的停顿会被当暂停而中途换源,换源期间逐帧会被吞。
- 角标:修后 HEVC 暂停 1 s 后 `原片 2160p · 暂停看原片`。

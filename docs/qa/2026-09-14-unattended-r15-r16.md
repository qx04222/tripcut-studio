### 2.2 4K 大文件性能(`perf-report.md`)

一条 5 分钟 2.1 GB 的 4K H.264 素材此前会被完整解码三遍(完整哈希 + 画质分析 + 运镜分析各一遍),
单进程硬件解码器只跑到 150 fps、CPU 闲着 65%。

| 阶段(秒) | 1080p 3 min 前→后 | 4K HEVC10 3 min 1.25 GB 前→后 | 4K H.264 5 min 2.1 GB 前→后 |
|---|---|---|---|
| 胶片条 | 1.4 → 0.3 | 2.1 → 0.8 | **7.0 → 1.1** |
| 画质分析 | 11.0 → 3.3 | 17.1 → 8.6 | **58.0 → 16.8** |
| 运镜分析 | 11.7 → 0.1 | 16.3 → 0.1 | **57.5 → 0.2** |
| **「分析完成」时刻** | 24.7 → **4.2** | 36.3 → **10.2** | 123.6 → **19.2** |
| **全部结束** | 40.1 → **20.1** | 60.1 → **30.1** | 185.3 → **80.1** |

做法:长素材按时间分段并行硬解(用此刻空着的解码许可,不额外占资源)、画质分析与运镜采样帧共用同一次
解码交接(逐字节验证一致)、胶片条改成只解 12 个关键帧(而非全片 `-skip_frame nokey`)、完整哈希优先级
从 58 降到 8(排到代理之后,避免 100 条 4K 素材要先顺序读 200 GB 才出第一张封面)。结果与改前逐值一致
(真 ffmpeg 断言场景切点、统计窗口、聚合量)。真机验证:30 s 4K HEVC 素材 `analyze_l1` 完成 +7.3 s(8-bit)
/ +10.4 s(10-bit),`analyze_motion` 交接帧 0.04–0.06 s。

## 5. R16:低配档与性能 Wave 1(RSS 实测数字)

来源:`.superpowers/sdd/r16/lane-perf-report.md`。所有数字取自 `perf_driver`,`TRIPCUT_MEMORY_BUDGET_
BYTES=8589934592`(8 GiB),R15 的 4K HEVC10 3 分钟 1.25 GB 夹具。

| | 总耗时 | 进程组 RSS 峰值 | 自家 ffmpeg 峰值并发 | 单进程峰值 |
|---|---|---|---|---|
| 改前(main,省内存档) | 40.5 s | 2101 MB | 3 | 994 MB |
| 改后(全部 8 个提交叠加) | **40.1 s** | **1091 MB(−48%)** | 2 | 1054 MB |

六项改动:
1. **自动档 v2**:`auto` 三选一——≤8 GiB「省电/低配」、<24 GiB「低」、≥24 GiB「标准」;低配档
   4K 并发解码许可 2、不借闲置解码槽、Whisper 默认 small、不起 OCR/CLIP 侧车。规格外的连带发现:
   胶片条关键帧解码默认用了多帧线程,单个 I 帧不需要,改 `-threads 1` 后单进程从 2.17 GB/0.52 s
   降到 **0.87 GB/0.44 s**。
2. **内存压力探测**改读 `kern.memorystatus_level`:本机同屏对照,内核口径 42–54% vs 旧口径(应用自算)
   24–28%,滞回常量(15/25)不变。
3. **预览小文件策略**:≤1080p H.264 且非 HDR/VFR、码率 ≤50 Mbps 的原片直接播放不再生成代理;
   32 GiB 预算下 R15 的 1080p 3 分钟 268 MB 夹具,`cache/` 从 72.7 MB 降到 **78 KB**,整条流水线
   20.1 s → 10.1 s,进程组 RSS 峰值 1055 → 778 MB。新增上限(默认 10 GB,可调 1–500)+ LRU 淘汰。
4. **前端 feed 引用稳定 + `React.memo(PoolCard)`**:10 秒空闲(5 次轮询、mock 60 条)下 ScriptDuration
   150 ms → **3 ms**,TaskDuration 157 ms → **5 ms**,JS 堆增量 +7.1 MB → +1.4 MB。
5. **散热三档退避**(`NSProcessInfo.thermalState`,不新增依赖)+「只在我不用电脑时做后台工作」开关
   (`CGEventSourceSecondsSinceLastEventType`,不需要辅助功能权限)。本机 M5 诱发不了热限流,靠注入
   文件覆盖三档做的单测;真机热限流验证留 Wave 2。
6. **mpv 低配参数表**:`demuxer-max-bytes` 64 MiB、`demuxer-max-back-bytes` 16 MiB、`cache-secs` 5、
   `scale=bilinear`、`dither=no`。单测确认本机 libmpv 全部接受;真机 4K 掉帧对比留 Wave 2。

**已知偏离**(车道报告原文):`low_spec_mode` 优先于 `memory_profile`(8 GB 机器手选「标准」不生效,
需把开关拨到「关」);淘汰代理后不自动重排任务(超限检查只在新代理落地时做);`paused_reason` 与
`proxy_bytes` 已在 API 上但状态条文案未接(属车道 A 文件所有权,留给接线人)。
